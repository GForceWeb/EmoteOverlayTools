A local tool.
A hosted business?

Cloud offers the easier customer journey and a stronger subscription model. Desktop offers lower operating risk and better local integration. The decision turns on willingness to pay and the work required to run a reliable service.

Based on the current working tree, including the in-progress direct Twitch integration. Prices checked 7 October 2026. All tables use USD unless marked AUD. Revenue figures are scenarios, not forecasts.

01

What customers actually gain

Downloaded · self-run Electron

More control, more setup

Download and install, launch the app, connect Twitch or Streamer.Bot, copy the localhost URL into OBS, and keep the app running.

  • Direct Twitch login already removes the need for Streamer.Bot in the current desktop changes.
  • Local settings, preview and testing work without your hosted service. Twitch events and uncached media still need internet.
  • Best fit for Streamer.Bot custom events, local automation, fixed versions and advanced workflows.
  • Installation, OS trust prompts, updates, port conflicts and forgetting to launch the app create support requests.
  • Moving to another streaming PC requires transferring or rebuilding settings.

Runtime server spend is minimal. Support, packaging and desktop maintenance still cost time.

Hosted · Twitch account only

One URL, fewer moving parts

Sign in with Twitch, grant scopes, choose settings, copy a persistent overlay URL into OBS, and run a test.

  • No separate app to install or keep open. The dashboard can close once OBS is connected.
  • Saved presets follow the broadcaster between machines. A browser dashboard supports remote management.
  • Updates reach everyone centrally. A release mistake can affect everyone at once.
  • OBS still renders animations on the streaming PC. Cloud does not fix local GPU or browser performance.
  • An outage, expired authorization or leaked overlay URL becomes the operator's support problem.

The current static GitHub Pages overlay still uses Streamer.Bot. It is not yet this Twitch-authenticated cloud service.

02

Host events, not video

The overlay already uses browser-side DOM and GSAP animations. It can stay a static browser app loaded by OBS. The server receives Twitch events, applies limits and settings, and sends compact events to the overlay. This model has no video encoding, stream relay, or per-viewer server connection.

Twitch EventSub→Verified webhook→Channel event router→OBS browser overlay

What can be reused

  • Animation modules, registry, shared configuration and browser rendering.
  • Twitch event mapping, after separating desktop infrastructure.
  • React settings and preview UI, replacing Electron IPC with authenticated APIs.

What must be built

  • Server OAuth, encrypted tokens, session cookies and per-account settings.
  • Entitlements, checkout, billing webhooks and deletion.
  • Tenant isolation, reconnects, duplicate suppression, rate limits and revocable overlay URLs.
  • Monitoring, backups, staged releases and rollback.
Can it really use just Twitch login?

Yes for the customer account. Use a confidential Twitch application and server-side authorization code flow. Login identity and permission to read channel events are distinct; a sign-in without event scopes is insufficient. The customer should see one consent journey rather than manage API keys.[1]

For a shared cloud chat reader, the operator authorizes a bot account with user:read:chat and user:bot. Broadcasters grant channel:bot plus the scopes needed for subscriptions, Bits, Hype Trains and rewards. Add chat-write permission only if needed. EventSub webhooks use an app access token with corresponding user grants.[2][3]

The documented 100-channel join limit has exceptions for broadcaster-authorized app-token chat subscriptions. It is not a blanket 100-customer ceiling. Confirm scope-specific requirements and channel eligibility live.[4]

Validate OAuth sessions at startup and hourly, refresh safely, and handle revoked permissions. Twitch tokens never belong in OBS URLs. Use a separate random read-only overlay key that the user can rotate.[5]

The architecture trap. The desktop uses an outbound Twitch EventSub WebSocket. Such sockets held open in Cloudflare Durable Objects cannot hibernate. One active object per broadcaster at 60 hours/month costs about $0.35 per active user before allowances. At 5,000 active users, billed duration alone is about $1,725/month. Prefer webhooks and hibernating inbound OBS sockets, or run persistent Twitch connections on conventional servers.[7][8]

Desktop WebSocket limits are per client ID and user ID: 3 connections, 300 subscriptions per connection, and a cost limit of 10. The current app uses one connection with 11 event subscriptions. These are not global user limits. Events lost during disconnection are not replayed.[6] In cloud, verify webhook signatures, deduplicate deliveries and discard stale animation triggers.[17]

Rates, formulas and what the low bill depends on

Workers Paid is $5/month including 10 million requests and 30 million CPU-ms. Overage is $0.30/million requests and $0.02/million CPU-ms. Model one webhook request and 5ms CPU per incoming event.[9] Durable Objects include 1 million requests and 400,000 GB-seconds. Excess costs $0.15/million requests and $12.50/million GB-seconds, rounded up to whole billing units. Model one router request and 10ms wall time at 0.128GB per event. Outgoing WebSocket messages are free.[7]

E = registered users × 0.50 active × 60 hours × 360 events/hour
Workers = 5 + max(0, E − 10 million) / 1 million × 0.30
          + max(0, E × 5 − 30 million) / 1 million × 0.02
DO requests = ceil(max(0, E − 1 million) / 1 million) × 0.15
DO GB-seconds = E × 0.010 seconds × 0.128 GB
DO duration = ceil(max(0, GB-seconds − 400,000) / 1 million) × 12.50
R2 storage = ceil(max(0, users × 0.1 GB − 10 GB)) × 0.015
Core bill = Workers + DO requests + DO duration + R2 storage

R2 includes 10GB storage, 1 million Class A and 10 million Class B operations, with free egress. Model 20 writes per registration and 2,000 reads per active user/month, with caching.[10] D1 includes 5GB, 25 billion rows read and 50 million rows written on Paid. Settings/token records average 10KB per account. No raw chat history or per-event DB read/write.[11]

The model assumes chat ingress during streaming hours. Around-the-clock chat subscriptions, heartbeats that prevent hibernation, slow async handlers and verbose logs increase costs. Filtering limits downstream animation triggers but does not erase webhook ingress charges. Two clients do not double Twitch ingress; model 10% of events producing triggers to both. Shared plan allowances may already be consumed by other projects.

Sell a reason to stay

Free overlays set a difficult price anchor. StreamElements advertises free cloud overlays and widgets.[12] Sound Alerts offers a free plan and a $6.99/month Premium tier with more reward and profile slots.[19] Streamlabs advertises a broader Ultra bundle starting at $15.75/month, not a directly comparable monthly-billed overlay plan.[13] These are pricing references, not evidence of demand for this project.

Cloud · proposed experiment

Free + $6/month

Free core emote effects and one preset. Pro adds multiple presets, custom media, scheduling, reward configuration and richer styles.

A$9 at planning FX. Test $60/year too; annual discounts reduce effective monthly revenue. Never interrupt a live overlay to upsell.

Desktop · proposed experiment

$29 once

A paid desktop edition or effects pack suits users who avoid subscriptions.

A$43.50 at planning FX. Paid upgrades need new value. A lifetime promise leaves ongoing support unfunded. Keep the free edition useful.

Either format · proposed prices

Packs & custom work

Test $10 to $25 themed packs, $150 to $500 commissions and $15 to $30/month team plans.

Packs need creative work and asset rights. Commissions sell labor. Teams need multi-channel demand, permissions and support.

Hosting alone is a weak paid feature. Animated emotes, playful avatar effects and the configurable animation library are better starting points. Presets and reward controls may earn payment when they save setup time. Ads and mandatory watermarks can undermine a broadcaster's live scene.

The desktop equivalent is a sales pipeline

At $29 once and 5% buyer conversion, the same populations generate $145 / $1,450 / $14,500 total gross sales. These are cumulative, not monthly recurring revenue. If 100 new qualified users arrive monthly and 5% buy, gross sales are $145/month. Existing buyers create support work without another payment.

Optional annual updates or a supporter membership need continuing value and a clear promise. Donations and sponsorship can support a community tool, but no amount is defensible without donor history. A paid desktop product can still need a small checkout/license backend.

Twitch Bits revenue is a separate opportunity through a Bits-enabled Twitch Extension. Merely listening to Cheers does not earn a developer share. Extension approval, channel eligibility and integration add scope, so this report does not include Bits income in the base case.[20]

Server break-even is the easy part

Each $6 domestic-card subscriber contributes about $5.66 before hosting and labor. Covering baseline hosting requires 6 / 11 / 36 paying accounts. At 1,000 registrations, adding 15 operator hours at $50 requires 144 paid accounts, or 14.4% of registrations. The base case has only 50.

At 10,000 registrations, the base leaves about $629/month after valuing 40 operator hours at $50. Funding $7,500/month of founder income plus $200 hosting needs about 1,361 paid users, before marketing and tax. That is 13.6% of registrations. Higher pricing, team sales or a larger user base may be needed.

Support is the larger cost risk. If 10% of active users need 15 minutes/month, support at $40/hour costs $50 / $500 / $5,000 monthly across the three scales. This is a stress assumption, not measured demand, and applies to either delivery model with different support causes. At assumed 5% monthly paid churn, 500 subscribers require 25 replacements each month just to stay flat. Retention and support time must be observed.

05

Decide with a priced pilot

Choose cloud when
  • Growth among casual streamers and recurring income are the main goals.
  • A pilot proves faster activation and real purchases.
  • Someone can own auth, billing and incidents during streaming hours.
  • The team accepts centralized credential custody and shared service risk.
Choose desktop when
  • The goal is a community utility or small side project.
  • Users value custom local actions and control.
  • The operator cannot commit to an always-available service.
  • One-time purchases appeal more than subscription retention.
  1. Measure the current journey. Track install, consent completion, first OBS test, weekly reuse and support requests. Ask what users would buy. The repo cannot establish demand.
  2. Prototype one cloud path. Consent, saved settings, one OBS URL and chat, raid and reward events. Test revocation, reconnect, tenant isolation and all 11 current event types before claiming parity.
  3. Run a 30 to 50-streamer pilot. Proposed gates: 70% complete an OBS test within five minutes, at least 10 pay or prepay for a defined Pro plan, and 60% still use it after four weeks. These are internal decision thresholds, not industry benchmarks.
  4. Prove stream reliability before growth. Measure regional event latency, reconnect recovery and support hours. Proposed target: p95 trigger latency under 500ms and zero cross-account events. Load-test raid bursts and rollback before recruiting 1,000 users.
  5. Keep migration voluntary. Import desktop settings and preserve local workflows. Reassess conversion, churn and cost per streaming hour after 90 days, then decide whether cloud becomes the default.
Budget the build separately. Author estimate for one experienced developer: 4 to 8 developer-weeks for a limited pilot, plus 4 to 8 for billing, hardening, migration and operations tooling. At 40 hours/week and $50/hour, that is $8,000 to $16,000 for the pilot and $16,000 to $32,000 total. This is a scope estimate, not a delivery quote. Live integration issues can add time.

Before selling, review permissions for EmoteRain-derived code, assets and libraries. The README credits the original author and no root license file was found in this working tree. That is a due-diligence gap, not a conclusion about commercial rights. Define upload limits, purchased-effect ownership and support promises before checkout.
